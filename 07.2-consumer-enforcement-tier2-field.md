# Step 7.2 — consumer enforcement: Tier 2 field-level

**Repos:** keeper, ant, squirrel, camel (repeat once per service, per entity with restricted fields)
**Needs sign-off:** no
**Depends on:** step 7.1 (`Can()` must exist and be wired for the base action)

## What

For entities with restricted fields (e.g. Ant order's `manager`, `status`; keeper app's `manager_id`, `status`; keeper user's `role`):

1. Base permission for the operation must already pass (Tier 1, e.g. `order.update`).
2. For each restricted field present in the request body, check the field-specific permission (e.g. `order.update.status`) before applying that part of the diff — otherwise strip or reject it.

## How (per protected entity, per service)

1. Enumerate the entity's restricted fields — search the handler for existing hardcoded field guards (e.g. keeper app handler's `manager_id`/`status` sysadmin-only checks, user handler's role-elevation guard) and convert each to a `Can()` call with the field-specific permission string.
2. Loop the request body's present restricted fields against `Can(user, service, appID, resource, action, field)` before writing each one — reject the whole request (400/403) rather than silently dropping fields, unless the plan for that entity says otherwise.
3. Leave unrestricted fields on the plain Tier 1 check — don't add field checks where none existed.

## Verify

- Unit test: field-restricted admin scenario from the Worked Example in `rbac-plan.md` (same fixture set as step 7.1).
- Manual: submit a restricted field as a role lacking the field permission — confirm rejection, and that the rest of the update still doesn't apply.
