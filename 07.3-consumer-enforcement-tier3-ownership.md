# Step 7.3 — consumer enforcement: Tier 3 ownership scope

**Repos:** keeper, ant, squirrel, camel (repeat once per service, per entity with own/any scope)
**Needs sign-off:** no
**Depends on:** step 7.1 (`Can()` must exist and be wired for the base action)

## What

`scope = 'own'` vs `scope = 'any'`, enforced at the DB query layer, not inside the authorization check:

- Role has the `any`-scoped permission → no ownership filter.
- Role has only the `own`-scoped permission → add `WHERE owner_id = user_id` at query build time (ent, e.g. `.Where(order.OwnerIDEQ(userID))`).

For list endpoints, apply this filter **before** `.Limit()/.Offset()` so pagination counts stay correct (project pagination convention).

Which column represents "ownership" is a per-entity mapping defined in each service's handler/repository code, not in the permission schema — e.g. keeper's `app` entity compares `id = jwt.app_id`, ant's `order` entity compares `manager_id = jwt.user_id`.

## How (per protected entity, per service)

1. Determine the owner column for this entity (see mapping above — confirm with the service's existing tenant/ownership convention, don't invent a new one).
2. In the repository layer, add a scope parameter to the query-building function(s) for this entity's read/update/delete paths.
3. In the handler/service layer, resolve whether the caller's role gives `any` or `own` scope for this resource/action (via the permission's `Scope` field from step 6's compiled map) and pass that down to the repository.
4. Branch on scope in the repository: `own` adds the `WHERE owner_id = user_id` filter, `any` doesn't. Apply before `.Limit()/.Offset()` on list queries.

- Manual: as a non-sudo `own`-scoped user, attempt to read/update another user's record — confirm 404/403, not a fetch-then-reject.
- `go test -race ./...` — this touches per-request query building; verify no races.
